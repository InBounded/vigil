Caught by actually re-running `pnpm check` twice in a row rather than trusting the first green run.

## 2026-09-22 — Squads v4 client generation (Codama)

`scripts/generate-squads-client.ts` runs `rootNodeFromAnchor` → `createFromRoot` → `codama.accept(renderVisitor(outDir, options))`, writing to `packages/core/src/squads/generated/`.

`renderVisitor`'s defaults scaffold a **standalone package** (its own `package.json`, plus an extra `src/generated/` nesting inside the given output directory) — appropriate for generating a client meant to be published on its own, not for generating code that lives inside an existing package like `@vigil/core`. Options were set to avoid that: `generatedFolder: "."` (write directly into `outDir`, no extra nesting), `syncPackageJson: false` (don't scaffold a `package.json` — `@vigil/core`'s own `package.json` already exists), `deleteFolderBeforeRendering: true` (so re-running the generator after an IDL update cleanly reflects deletions, not just adds/edits), `importExtension: "js"` (required — this project's `tsconfig.base.json` uses `moduleResolution: "NodeNext"`, which needs explicit `.js` extensions on relative imports; the default omits them).

The generated account discriminator for `Multisig` (`[224, 116, 121, 186, 68, 161, 79, 236]`) was cross-checked against an independent computation of `sha256("account:Multisig")[:8]` done during fixture-hunting, before this generator existed — the two agree, which cross-validates both the generator's output and the manual decoding done earlier to find fixture candidates.

**Runtime dependency found missing, not assumed**: the generated code imports from `@solana/program-client-core`, which `renderVisitor` would normally have added to the scaffolded `package.json` it was told not to generate. Running `pnpm --filter @vigil/core run typecheck` surfaced this immediately as `TS2307: Cannot find module`, rather than it being silently missing. Added to `@vigil/core`'s real `dependencies` at `8.3.0`, matching the rest of the `@solana/kit` family and confirmed current via the npm registry.

`biome.json` gained two `overrides` entries rather than editing generated output by hand (which the generated files themselves say not to do, and which `scripts/generate-squads-client.ts` would silently undo on the next run anyway):
- `packages/core/src/squads/generated/**`: turns off `style/noNonNullAssertion` and `complexity/noBannedTypes`, the only two lint rules the generated client's accessor/error-formatting code legitimately trips (confirmed by reading each flagged line, not blanket-suppressed). Formatting and import order are still enforced and were auto-fixed with `biome check --write` right after generation — re-run that after every regeneration.
- `packages/core/idl/**` and `fixtures/**`: formatter turned off entirely. These are captured upstream artifacts (the IDL's `docs/DECISIONS.md`-recorded SHA-256, and fixtures' real on-chain bytes) — reformatting them would risk silently drifting their bytes from what was actually fetched/captured.

## 2026-09-22 — Token-2022 decoder is hand-written (maintainer decision), with a corrected size rationale

Decision (maintainer, 2026-09-22): hand-write the Token-2022 decoder, fully decoding every instruction that sets or changes an authority, including extension instructions; keep `@solana-program/token-2022` as a dev dependency for cross-checking only.

**Correction to the rationale given when proposing this.** The plan said the official client would "load ZK crypto into the browser". Measured with esbuild (`--bundle --minify --format=esm --platform=browser`, the same esbuild `tsx` ships), that is not true for parsing — tree-shaking drops the confidential-transfer code:

| Bundle | Minified | gzip -9 |
|---|---|---|
| kit baseline (`getAddressDecoder` only) | 35.2 KB | 11.2 KB |
| `parseToken2022Instruction` from `@solana-program/token-2022@0.19.0` | 96.3 KB | 19.3 KB |
| our `token2022Decoder` | 43.8 KB | 13.7 KB |

So the official parser costs ~61 KB minified / ~8 KB gzip over the kit baseline versus ~8.5 KB / ~2.5 KB for ours. The remaining reasons to hand-write are therefore (a) that size difference, and (b) keeping the production dependency tree small: the official package brings runtime dependencies on `@noble/curves`, `@solana-program/record` and `@solana-program/zk-elgamal-proof`, plus a peer dependency on `@solana/zk-sdk`, none of which a read-only parser needs. The trade-off accepted: we own ~350 lines of layout code. It is mitigated by `token-2022.test.ts`, which builds 75 instructions with the official client's own builders and asserts our name, arguments and account roles equal the official parser's, for every instruction we fully decode (including `SetAuthority` for all 18 authority types, set and removed).

Scope of full decoding: base instructions (0–20 except 21, plus 22, 25, 35, 38), `SetAuthority` for all 18 `AuthorityType`s, `Initialize*`/`Update*` for TransferHook (36), MetadataPointer (39), GroupPointer (40), GroupMemberPointer (41), Pausable (44: initialize/pause/resume), Token Metadata `UpdateAuthority` and Token Group `UpdateGroupAuthority` (8-byte interface discriminators, checked three ways: program source, official client constants, and our own `sha256("<namespace>:<name>")[..8]`), and `Batch` (255, recursively). Every other extension sub-instruction is identified by name only and reported with an `INSTRUCTION_ARGS_NOT_DECODED` gap, so it never looks fully understood.

Layout sources: `solana-program/token-2022` at commit `f0d526508a9fa7e638b9aca1800d9c504ed87335` — `interface/src/instruction.rs` (`unpack_with_rest`, `AuthorityType::from`, `unpack_pubkey_option` = 1-byte tag + 32 bytes), `interface/src/extension/*/instruction.rs` (`MaybeNull<Address>` = 32 bytes, all-zero = none), `program/src/processor.rs` (`process_batch` item layout; dispatch order: 1-byte tag first, then Token Metadata, then Token Group).

Role names follow the official client where they differ from what we first wrote (caught by the cross-check test): `syncNative` takes an optional `rent` account (confirmed in `process_sync_native`); the TransferHook update and pause/resume authority role is `authority`.

## 2026-09-22 — Phase 3A decoding pipeline design

- **Contract additions** (`packages/core/src/report.ts`): only `Provenance`, `DecodedInstruction`, `DecodedAccount`, `AnalysisGap` exist so far; the rest of `AnalysisReport` is a later phase. Two additions to the `AGENTS.md` contract: `DecodedInstruction.inner?: DecodedInstruction[]` (instructions carried inside another: the message of a Squads `vaultTransactionCreate`/`batchAddTransaction`, or the items of a Token `Batch`), and an `AnalysisGap` shape `{ code, message, instructionIndex?, address? }` with a closed set of codes, since `AGENTS.md` names `AnalysisGap` without defining it.
- **Account index resolution** is shared by Solana wire messages and Squads messages: static keys, then all lookups' writable entries, then all lookups' readonly entries. Confirmed for Squads in `utils/executable_transaction_message.rs` (`get_account_by_index`, squads-protocol/v4 at the pinned commit), and for Solana by comparing against `meta.loadedAddresses` of a real v0 transaction in `squads-fixtures.test.ts`.
- **Squads compact message format** (`parseSquadsTransactionMessage`): from `instructions/vault_transaction_create.rs` and `utils/small_vec.rs` at the pinned commit (`SmallVec<u8, _>` everywhere except instruction data, `SmallVec<u16, u8>`), with the program's own `TryFrom` validation applied. Cross-checked against `@sqds/multisig`'s encoder and its beet deserializer, and against real mainnet data (raw creation transaction vs. the stored `VaultTransaction` it created).
- **Lookup-table resolution** fetches tables with one `getMultipleAccounts` per round. Decoding is pure; a round that meets a table it hasn't fetched yet records it, then the pipeline fetches and re-decodes. Tables can only be discovered one embedding level deeper per round, so rounds are bounded by `MAX_EMBEDDED_DEPTH` (3). A missing, foreign-owned, uninitialized or malformed table, or an index past its end, is a gap; affected instructions are shown as undecoded with no accounts rather than with guessed ones.
- **Instructions whose program address can't be resolved** (only possible inside a Squads message, where program IDs may come from lookup tables) are omitted from `instructions` but recorded as an `ACCOUNT_UNRESOLVED` gap with their top-level index.
- **Summaries** are generic: `ix.<program>.<instruction>` with every scalar argument and every named account role as string params; `null` becomes `"none"` so an authority being removed is explicit. Wording is the UI's job.
- **Strings are not sanitized here.** Memo text and Squads memos are returned raw in `args`; the sanitizer is a later phase and must run before any interface renders them.
- **Transaction buffers**: `transactionBufferCreate`/`Extend` and `vaultTransactionCreateFromBuffer` carry only a chunk (or none) of the message; they are decoded, and an `EMBEDDED_MESSAGE_IN_BUFFER` gap says the proposal content was not shown.

## 2026-09-22 — Third-party IDLs (3B.1)

- **Where**: for a program with no built-in decoder, Vigil reads, in one `getMultipleAccounts` call, (1) the canonical Program Metadata account for seed `idl` (PDA of `ProgM6JCCvbYkfKqJYHePx4xxSUSqJp7rh8Lyv7nk7S` with seeds `[program, <None → zero bytes>, "idl" padded to 16 bytes]`, cross-checked against `findMetadataPda`) and (2) the Anchor IDL account (`create_with_seed(find_program_address(&[], program), "anchor:idl", program)`). Program Metadata wins; the Anchor account is the fallback, **also when the Program Metadata account exists but is unusable**. Lookups run after lookup tables resolve, inside `decodeMessageWithLookups` (new optional `DecodeOptions { idl?: IdlOptions | false }`, threaded through `decodeRawTransaction` and `decodeVaultTransactionMessage`).
- **Not followed (maintainer decision)**: Program Metadata data stored at a **URL** is never fetched (outside the RPC allowlist, and a phishing vector); it produces the `IDL_AT_URL` gap, whose plain-language text tells the signer the program's own description could not be read and the instruction's effect is unknown. Data stored in **another account** (`External`) produces `IDL_UNSUPPORTED`. *Possible improvement*: support `External` (one more allowlisted account read) if it turns out to be common.
- Also refused, as `IDL_UNSUPPORTED`: YAML/TOML formats and non-UTF-8 encodings; as `IDL_INVALID`: non-canonical accounts, wrong owner, wrong discriminator, a different `program` field. `format: None` is accepted when the content parses as JSON (Whirlpool, Raydium CPMM and marginfi publish their IDL with `format: None`).
- **Limits**: compressed payload ≤ 1 MB (checked from the length field before reading); inflate is streamed in 1 KB input slices and stopped as soon as output exceeds 5 MB (deflate expands ≤ ~1032:1, so at most ~1 MB is produced past the check); `JSON.parse` only; minimal structure checks; a read **timeout** (default 10 s) on the IDL account fetch → `IDL_FETCH_FAILED`.
  - Decoding with an IDL is synchronous and cannot be interrupted by a timer, so instead IDLs that could make it hang are refused up front: any array/set/map whose items take zero bytes (a `u32`-prefixed vector of empty structs would loop up to 2³² times). *Known limit*: decoding cost is otherwise bounded by instruction size (≤ 1,232 bytes, or a v1 transaction's size).
- **Content validation**: every `name` in the raw Anchor JSON and every node name after conversion must be a plain ASCII identifier (`[A-Za-z_][A-Za-z0-9_]{0,127}`). Checked on the raw JSON too because the conversion camel-cases names and silently drops characters it does not understand (`tr\u0430nsfer`, with a Cyrillic `а` (U+0430), would otherwise become the ASCII `trNsfer`). The 128 limit (not 64) is because real IDLs have long names (pump.fun: a 70-character error name). An IDL declaring another program address is refused; other programs bundled in an IDL are dropped; the IDL is pinned to the program it was read for.
- **Provenance**: instructions decoded from an IDL have `decoder: "anchor-idl" | "program-metadata-idl"` and `provenance: "idl-declared"`, including argument and account names. Their summary is the generic `ix.idl.call` ("Calls “x” on a program with no built-in decoder … not verified"). The IDL's own program name is never used as `programLabel` (a program could name itself `squadsMultisigProgram`); `programLabel` comes only from the registry.
- **Cache**: `IdlCache { get, set }` in core, key `<program>:<sha256 hex of the IDL account data>`; value = the validated JSON text, which is **re-validated on every read** (a tampered cache is treated like chain data). Cache errors are ignored. Implementations, not yet wired to core (the CLI and web phases do that; each declares the same two-method interface structurally instead of importing core, which would need the workspace build order sorted out first):
  - CLI `FileIdlCache` (`packages/cli/src/idl-cache.ts`): `$XDG_CACHE_HOME/vigil/idl/` (a relative `XDG_CACHE_HOME` is ignored, per the XDG spec) or `~/.cache/vigil/idl/`; directory `0700`, files `0600`, atomic write (temp + rename), keys validated by regex so nothing escapes the directory, entries > 5 MB ignored.
  - Web `IndexedDbIdlCache` (`apps/web/src/idl-cache.ts`): database `vigil`, store `idl`, total cap 20 MB (default), least-recently-used eviction, injected clock; any IndexedDB failure behaves as an empty cache.
- **Noise**: `@codama/nodes-from-anchor` prints "PDA name collision" warnings to stderr for some real IDLs (pump.fun, Whirlpool). Harmless; not suppressed (that would mean patching `console`). The CLI phase may want to capture it.

- §6/§10: the Anchor IDL account discriminator is `sha256("internal:IdlAccount")[..8]`, **not** `sha256("account:IdlAccount")`: `IdlAccount` is declared `#[account("internal")]`, and a namespace argument replaces the `account` prefix (`lang/attribute/account/src/lib.rs`, `gen_discriminator(namespace, account_name)`, anchor commit `cc9f6b1c5e4a646bc592486a7bd485a8357a028d`). ## 2026-09-22 — Sanitizer (3B.3)

- `sanitizeOnchainString(s, kind = "text")` → `{ text, modified, flags }`, `kind` ∈ `name`/`symbol` (64 code points), `memo`/`text` (512). Also applied to declared token names/symbols and to imported user labels.

Decided on the Phase 4 plan (recorded as given):

## 2026-09-22 — Phase 4: risk rules engine — design

- **Layout** (`packages/core/src/rules/`): `types.ts` (`Rule`, `RuleContext`, `RuleOptions`, `RuleFacts`), `options.ts`, `context.ts` (`createRuleContext`: resolves options, derives vaults, builds the known-address registry; async only for PDA hashing), `walk.ts` (every instruction, nested ones included, with path, top-level index and the proposed marker), `helpers.ts`, `catalog/{critical,config,warning,info}.ts` (27 rules), `engine.ts` (`RULES`, `runRules`, `computeVerdict`), `docs.ts`, `skeleton.ts` + `confusables.generated.ts`.
- **Rule shape**: `{ id, name, defaultSeverity, titleKey, variants, docs: { what, why, falsePositives }, evaluate }`. `variants` lists every `<titleKey>.<variant>` a rule can emit so tests prove every one has text in both languages with the same placeholders. `name` was added to the phase's shape for the generated documentation.
- **Findings**: `titleKey` + string `params` (addresses, base-unit amounts with `decimals`/`mint`/`symbol`, old and new values); `evidence` is `field: value` lines (facts, not translated; each finding about an instruction ends with `instruction: <path>`, e.g. `1.0` for the first instruction inside instruction 1); `instructionIndex` is the top-level instruction. Provenance: the instruction's own for instruction findings (`onchain`, or `idl-declared`), `onchain` for account data (multisig, proposal, buffers, token metadata), `external-api` for an unverified program, `simulation` for W006/W007, `rule-inference` for comparisons (C008, C010, W001, W004, W005, W011, W002 with unknown status).
- **Order** (`runRules`): VGL-W011 first (always, per the phase), then critical, warning, info; within a severity report-level findings first, then by instruction, then rule id, then the order the rule produced them (stable sort). **Verdict** exactly as in `AGENTS.md`.
- **Known addresses** (`RuleContext.known`, address → reasons): this multisig, its members and derived vaults, registry programs, registry tokens of the report's cluster, user known addresses, recent destinations.
- **Options**: `largeTransferPercent` (default 10; 0 < p ≤ 100, at most two decimals; converted to basis points so every comparison is bigint), `largeTransferAbsolute` (per asset, base units, > 0), `historyDepth` (default 0 = off; at most 1,000 = `MAX_GET_CONFIRMED_SIGNATURES_FOR_ADDRESS2_LIMIT` in agave `rpc-client-types/src/request.rs:155` at `e3fdd18f`, one `getSignaturesForAddress` page), `knownAddresses`. Invalid values throw `RuleOptionsError` (`INVALID_RULE_OPTIONS`).
- **Proposed marker, refined on real data**: several real fixtures create, approve **and execute** a Squads transaction in one atomic transaction (`config-transaction*.json`, `squads-create-with-lookup-table.json`). There the change happens now, so "proposed only" would be false. An embedded message (or config actions) is marked proposed only when the analysed transaction does not also execute the same Squads `transaction` account (`vaultTransactionExecute` / `configTransactionExecute` / `batchExecuteTransaction`, role `transaction` in the generated client).
- **Registry programs** (native programs, SPL Token, Squads, Memo) are curated and skipped by VGL-W002 / W003; otherwise every Squads raw transaction would warn about the Squads program itself.
- **VGL-C008 (address poisoning)**: compares every address the transaction mentions (accounts, address arguments at any depth, token-account owners, config actions) against the known addresses. **False alarm found on real data and fixed**: `StakeConfig11111111111111111111111111111111` shares `Stak…1111` with `Stake11111111111111111111111111111111111111` (`native-instructions.json`, rfo8UEYu). An address ending in twelve or more `1`s is never reported: it is constructed (native programs, sysvars), and matching twelve fixed base58 characters would take about 58¹² ≈ 10²¹ key or PDA attempts, so an attacker cannot produce one. A poisoned look-alike of such an address (random middle) is still reported.
- **VGL-C006**: config proposal actions (`configActions`), `configTransactionCreate` actions, and the direct config-authority instructions (`multisigAddMember` … `multisigSetConfigAuthority`). Actions are re-decoded from the instruction's own bytes with the generated Squads codecs (typed per the IDL, no hand validation). "Lowered" compares with the current multisig only when the instruction targets the analysed multisig. A spending limit on mint `Pubkey::default()` is SOL (Squads v4 `spending_limit_use.rs` at `af94153f`); empty `destinations` = any address (IDL doc). The `ConfigAction` report type is camelCase (`kind: "addMember"` …) and adds `setConfigAuthority` (direct instruction only).
- **VGL-C007**: `SetLockupChecked` takes the new custodian from account 2, not from data (solana-program/stake `interface/src/instruction.rs` at `6ff57404`, `set_lockup_checked`); `@solana-program/stake@0.10.0` does not name that account. Vote-account authority changes cannot be detected (Vote is not decoded, Phase 3A decision); they show as VGL-W001.
- **VGL-W004**: counts System `transferSol` / `transferSolWithSeed` and Token / Token-2022 `transfer` / `transferChecked`, summed per (proposed?, sender, asset) so splitting a payment does not hide it. The sender is the source for SOL and the transfer `authority` for tokens; the balance to compare is whatever the gatherer provides for that sender and asset. **Limits**: a token transfer signed by a *delegate* is compared with the delegate's balance (the gatherer must provide it, or add the gap); `transferCheckedWithFee` is only identified (its arguments are not decoded, which is already a gap); stake/nonce withdrawals and Squads `spendingLimitUse` are not counted.
- **VGL-W007**: a balance change is explained when its account is writable in some decoded (non-opaque) instruction; a decrease of the fee payer's SOL (the fee) is not reported.
- **VGL-W008**: compares declared symbol and name with the registry tokens of the same cluster after NFKC, mapping look-alike characters to the ASCII letter or digit they resemble, lower-casing and keeping letters and digits. Two forms (map then lower-case, lower-case then map) because the table is case-sensitive (`I` → `l`, `i` unmapped). Also fires on the sanitizer's `non-ascii`, `mixed-scripts`, `invisible-removed`, `bidi-removed`, `zero-width-removed`, `control-chars-removed` flags. *Known limit*: UTS #39 does not treat `1` as confusable with a lower-case `i` (`J1toSOL` is not matched; `JIT0SOL` is).
- **VGL-W009**: only instruction 0 counts, as in the runtime: `uses_durable_nonce` checks the instruction at `NONCED_TX_MARKER_IX_INDEX` (= 0) is a System `AdvanceNonceAccount` (anza-xyz/solana-sdk `transaction/src/versioned/mod.rs` and `transaction/src/lib.rs` at `43339f08`).
- **VGL-I001**: maximum priority fee = `ceil(price × min(limit, 1,400,000) / 1,000,000)` lamports, as agave `get_prioritization_fee` (`compute-budget/src/compute_budget_limits.rs`), with `MAX_COMPUTE_UNIT_LIMIT = 1_400_000` (`program-runtime/src/execution_budget.rs`) and the `.min(MAX_COMPUTE_UNIT_LIMIT)` cap (`compute-budget-instruction/src/compute_budget_instruction_details.rs`), agave commit `e3fdd18f`. Checked on a real transaction: 812,534 × 492,287 → 400,000 lamports. Only top-level instructions of a base64 transaction set the fee; inside a proposal they are reported as having no effect (the Compute Budget program's processor is a no-op, `programs/compute-budget/src/lib.rs`). A v1 transaction's inline `priorityFeeLamports` is shown as is. *Not flagged*: duplicate Compute Budget instructions (the runtime rejects the transaction; the last one is shown).
- **VGL-I004 / I005** follow the Squads v4 program at `af94153f`: execution needs `Approved` and `now − approved_at ≥ time_lock` (`vault_transaction_execute.rs`, `config_transaction_execute.rs`, `batch_execute_transaction.rs`); stale config transactions can never execute, stale vault/batch transactions can if approved before becoming stale; stale proposals cannot be approved or rejected (`proposal_vote.rs`). I005 fires on Rejected / Cancelled / Executed, stale config proposals, and stale vault/batch proposals not yet approved.
- **Renderer** (`i18n/render.ts`): `renderFinding(finding, locale, instructions)` (labels from the report's instructions, nested ones included; a missing sentence is reported as missing, not invented). `renderSummary` now shares `renderTemplate` with it; its behaviour is unchanged (all existing summary tests pass). New placeholder types: `text` (verbatim), `duration` ("1 d 1 h"), `permissions`, and any other `{x:type}` looks up `<type>.<value>` (`verification.*`, `period.*`, `gap.*`, `hash.*`); an `address` param of `unknown` is shown as "unknown".
  - **Fidelity fix**: an untyped param equal to `"none"` is rendered as the translated word "none"/"nenhum". On-chain text in finding sentences (memo, simulation detail, declared token name and symbol) therefore uses `{x:text}`, so a memo that literally says "none" is shown as written. (Instruction summaries from Phase 3B still use untyped params; not changed.)
- **Confusables table**: generated by `scripts/generate-confusables.ts` from Unicode **18.0.0** `https://www.unicode.org/Public/18.0.0/security/confusables.txt`, SHA-256 `6ed3ee967c9dfdf6677d563c9985182fbc50a2efb7d6059cd57b2e2ce18f5b92` (checked by the script). Keeps the 1,586 single-character mappings to one ASCII letter or digit; keys are written as `\u{…}` escapes so the file never contains the look-alike or invisible characters. 32 KB of source; no new dependency.
- **`docs/rules.md`** is generated by `pnpm docs:rules` (`scripts/generate-rules-doc.ts`) from each rule's `docs`; a test fails if the committed file differs.
- **Contract changes** (`report.ts`): `Severity`, `Verdict`, `Finding` as in `AGENTS.md` (with `titleKey` variants and `params.proposed`); `AssetId` (`"SOL"` or a mint; `"SOL"` can never be a base58 address); minimal `ProgramInfo` (`upgrade`: immutable / upgradeable with authority / unknown, `programData?`, `executableHash?`, `verification`), `BalanceChange`, `SimulationResult` (success with balance changes / failed / unavailable; absent = not attempted), `ConfigAction`, `SpendingLimitPeriod`; gap codes `SIMULATION_DISABLED`, `PROGRAM_VERIFICATION_UNKNOWN`, `TRANSFER_BALANCE_UNKNOWN`. Phase 5 may extend `ProgramInfo` / `SimulationResult` when it fills them.
- **Tests**: every rule has positive and negative tests. Instructions are encoded with the official builders (`@solana-program/*`, the generated Squads client) and decoded by Vigil's own decoders; hand-built instructions only cover shapes a decoder cannot produce (missing accounts). Every rule also runs over real mainnet fixtures (`rules/fixtures.test.ts`): the program-upgrade proposal (raw and through `SquadsV4Adapter`), both atomic config transactions, the token-transfer proposal (IDLE transfers summed; five real non-registry tokens raise no VGL-W008), the 1-of-12 multisig with an opaque program, the durable-nonce transaction, v1 transactions, lookup tables. Facts only gathered in Phase 5 (balances, buffers, simulation, verification, history) are given by hand in those tests, and say so. The **routine proposal** test uses the real 50 USDC `transferChecked` (3Feg3sty) as an Active proposal's content, with the destination a known address, a 5,000 USDC balance and an explained simulation: verdict `no-findings`, only VGL-I004 (info).
- **Test support**: `packages/core/src/test-support/` holds shared test builders; excluded from the build (`tsconfig.json`) and from coverage. It uses `@solana/kit`'s `createNoopSigner` only because the official builders type signer accounts as `TransactionSigner`; it never signs anything.
- **Observation (not changed, earlier phase)**: a registry-mint `transferChecked` whose mint account was not read (real USDC transfer in `native-instructions.json`) gets `mint` and `decimals` in its summary params but no registry `symbol`, so it is rendered as "50 of token EPjF…Dt1v" rather than "50 USDC". ## 2026-09-23 — Phase 5: simulation design

- **Building** (`simulate/build.ts`, `vault.ts`): the Squads message's accounts are resolved against its lookup tables (all must resolve, else `unavailable: accounts-unresolved`), each account keeps the message's signer/writable flags, and kit (`compressTransactionMessageUsingAddressLookupTables`, `compileTransaction`) builds a v0 transaction reusing the original tables. The vault and ephemeral PDAs are signers with 64 zero bytes (kit's encoding of a missing signature). The recent blockhash is a fixed placeholder (32 zero bytes) that `replaceRecentBlockhash` replaces; this keeps the bytes deterministic so recorded simulations replay exactly. Over 1,232 bytes → `unavailable: too-large`, never sent.
- **Fee payer**: the vault if it holds at least the estimated fee (5,000 × signatures); otherwise the Execute member with the most SOL (`simulation.note.feePayerMember`, reason `vaultBalance`); if nobody can → `unavailable: no-fee-payer`. **Decision taken here (please confirm)**: when the vault-paid simulation *fails* and an Execute member can pay, it is simulated again with the member paying and that result is reported (reason `vaultFailed`) — in a real execution the executing member pays the fee, and a vault spending its whole balance would otherwise fail only because of the simulation's own fee. Both attempts are real RPC calls.
- **Pre-state / post-state**: one `getMultipleAccounts` of every writable account (plus the vault and Execute members) gives the pre-state and slot `S`; the simulation runs with `minContextSlot: S` and returns the post-state of the writable accounts. Mints are read afterwards for decimals (registry fallback, else `TOKEN_DECIMALS_UNKNOWN`). Cross-check (maintainer decision): the RPC's own `preBalances` / `preTokenBalances` are compared with the pre-state read; any difference is a `SIMULATION_PRESTATE_MISMATCH` gap per account, and the values shown stay the pre-state read's.
- **Balance changes**: SOL and Token/Token-2022 base layout, exact bigint base units, `decimals`, labels of the account and of its holder (token owner, or the account for SOL), sorted by holder so changes group by who is affected (`groupBalanceChanges`). The fee payer's SOL excludes the fee (`feeExcluded`, RPC-reported fee, else the estimate; `simulation.note.feeExcluded` says which). Created/closed accounts are marked.
- **Notes and snapshot requirement** (maintainer): every result carries `simulation.note.snapshot` first; `renderSimulationNotes` always emits it first even if a result object lacks it, so no interface can show balances without "Network state can change before execution … not a guarantee". Other notes: fee excluded, member fee payer, raw fee payer, extra signer, batch isolation, inner instructions unavailable, logs truncated, balances not reported.
- **Failures never throw**: RPC refusal (JSON-RPC error) → `rpc-refused` with the server message; transport failure → `rpc-error` with at most the HTTP status (a transport message can contain the endpoint URL and its API key); each `unavailable` adds a `SIMULATION_UNAVAILABLE` gap; missing post-state → success with no changes plus `SIMULATION_BALANCES_INCOMPLETE`.
- **Batches**: every item is simulated on its own (`BatchSimulation`, note `simulation.note.batchIsolated`). **Config proposals** are not simulated (no outcome, no gap). **Base64 mode** simulates the input as-is; its own fee payer pays.
- **Logs**: sanitized per line (`text` kind: 512 code points), first 200 lines; `logsTruncated` means lines were dropped or cut.
- **Inner instructions** are requested; only their program ids are kept (`innerPrograms`), for program information.
- **Known limits**: Compute Budget instructions inside a Squads message run at top level in the simulation (in a real execution they are no-op CPIs), so a low `SetComputeUnitLimit` in a message could make the simulation fail where execution would not; the simulation uses the default compute budget; balance changes cover writable accounts only (read-only accounts cannot change).

## 2026-09-23 — Phase 5: program information design

- **`list`** (D4): walks the latest `--limit` indices (default 20, max 100); pending = not stale, a transaction account exists, and no proposal account yet or status Draft / Active / Approved / Executing. `--status active` (default) shows pending ones; `all` also lists the others, not analysed (simulating what already happened says nothing). One analysis at a time, one shared `VerificationCache`.
- **Input validation**: base58 alphabet, then kit `isAddress`; index `^[1-9][0-9]*$` up to `u64::MAX`; base64 standard alphabet with padding, whitespace ignored, at most 5,464 characters (the encoding of 4,096 bytes, the v1 limit); stdin capped at that plus 4 KB; `--history` 0–1,000; option values checked against their lists; command-only options (`--tx`, `--limit`, `--status`) refused elsewhere; `--history` refused with `--tx`.
- **Language**: `--lang en|pt` (`pt-PT` accepted), else `LC_ALL` → `LC_MESSAGES` → `LANG` (`pt*` → European Portuguese), else English. The report, headings and progress are translated; **help texts, error messages and rule explanations (`explain`, from `docs/rules.md`'s source) are English only** for now.
- **`--cluster`** only picks the default endpoint; if the RPC's genesis hash says otherwise, a note goes to stderr and the report uses the real cluster.
- **Release workflow** (`.github/workflows/release.yml`, used in Phase 10): only on `v*` tags; actions pinned by the SHAs above (`setup-node` `registry-url` input confirmed in its `action.yml` at the pinned SHA); job-level `id-token: write` (provenance) and `contents: read`; a `npm` environment so the maintainer can require an approval; no dependency cache; checks the tag equals both package versions; runs `pnpm check`; `pnpm -r publish --access public --provenance --no-git-checks` (pnpm 12.5.1 `publish --help` lists `--provenance`; recursive publish skips private packages). Authentication: `NODE_AUTH_TOKEN` from an `NPM_TOKEN` secret through the `.npmrc` that `setup-node` writes. **Not verified here** (to check in Phase 10 with the real organisation): that pnpm 12 reads that `.npmrc` token, and whether npm trusted publishing (OIDC, no token) can replace the secret.
- **Found and fixed while reading real output**: the English Associated Token Account summaries said "Creates the the USDC mint token account" (template "the {mint}" + label "the USDC mint"); now "Creates token account {ata} of {mint} for {owner}". A default RPC URL was compared unnormalised with a user URL (`…com` vs `…com/`), so the "cross-check RPC equals primary" guard could miss it; normalised. Writing to a pipe whose reader had closed (`vigil … | head`) crashed with an unhandled `EPIPE`; output now stops quietly and the command keeps its exit code (spawn test).

## 2026-09-23 — Phase 7: web app design (`apps/web`)

- **Presentation only.** Every sentence, verdict text, gap, config action and rule explanation comes from core (`renderSummary`, `renderFinding`, `CATALOGS`, `RULES[].docs.why`); the multisig page's weaknesses are core's own VGL-W010 rule run on a context holding only the multisig (`src/analysis/health.ts`). The web app never judges.

A build test checks the entry chunk does not contain the engine.

The start page's one field is an address if it is one, otherwise a base64 transaction.

- **Settings** in `localStorage` under the single key `vigil.settings` (never `localStorage.clear()`: on a GitHub Pages user site the origin is shared with other pages). Read back through `validateSettings`, field by field, since other pages of the origin can write there. **The offline file never stores RPC endpoints** (kept in memory only; its `file://` storage is readable by any other local HTML file). Known addresses: added in the page or imported with core's `parseUserLabels` (the `vigil-labels` format), exported with `serializeUserLabels`; labels cleaned (`safeText`, 100 characters). History depth default 0 (core's default). Absolute large-transfer thresholds for SOL (lamports) and USDC/USDT (mainnet mints from core's registry; the registry has no devnet mints, so they do not apply on devnet), typed in whole units and converted with exact integer arithmetic.

Sentences are core's sentences rendered with `addresses: "full"`; `TextWithAddresses` turns each base58 run that passes `isAddress` into an `Address`. **Address poisoning**: every VGL-C008 finding's `{ address, resembles }` pair is highlighted wherever the address appears, with differing characters in `<mark>`, and the finding shows the two addresses one above the other.

W011 still cannot be missed: the verdict banner already says "Analysis incomplete" and the "Not checked" list follows the findings.

Filtering by code point, not a regular expression (Biome's `noControlCharactersInRegex`).

## 2026-09-24 — Phase 8: sources confirmed

Checked on 2026-09-24 against the official documentation:

- **Discord Execute Webhook** (docs.discord.com/developers/resources/webhook): `POST /webhooks/{id}/{token}`, `wait` query parameter (with `wait=true` the created message is returned, else `204`), `content` "up to 2000 characters", `allowed_mentions`, `flags` (only `SUPPRESS_EMBEDS`, `SUPPRESS_NOTIFICATIONS`, `IS_COMPONENTS_V2` allowed). ## 2026-09-24 — Phase 8: design

- **Core** (`packages/core/src/watch/`, no I/O except through the injected `RpcClient`): `readWatchSnapshot` (`getGenesisHash`, `getAccountInfo`, `getMultipleAccounts`: allowlisted only) reads the new indices (at most 100 per cycle; more are reported as skipped and counted as seen, with a warning to run `vigil list`) and every tracked index. `detectChanges(snapshot, previousState)` is pure. Events: `new-proposal` (every index above the last seen; on the first run only pending ones; a transaction already closed when first read is still reported, `status: "Closed"`, so nothing disappears silently) and `status-change` into Approved, Executed, Rejected, Cancelled, or `Closed` when a tracked proposal's accounts vanished (its final status could not be read). A step skipped between two reads (Active → Executed) is one change; nothing in between is invented. Other transitions (→ Draft, → Active, → Executing) update the state silently. Tracking ends when a proposal is final, stale (logged, not alerted: the phase did not ask for it) or closed. A state of another multisig or cluster is refused (`WatchError`).
- **What is analysed**: new pending proposals and proposals that became Approved (re-analysed: the simulation must reflect the state at "ready to execute"); Executed/Rejected/Cancelled/Closed alerts carry the last known verdict, labelled as such. A failed analysis still sends the alert, saying so (only `AnalysisError` messages, which hold no URL). Approved with a time lock: the alert says when execution becomes possible (approval timestamp + time lock).
- **State file** (`vigil-watch-state` v1): core's watch state, last verdict per tracked index, and the outbox (alert + notifiers still pending + queue time). Read back field by field, queued alerts included (they are formatted and sent again). Written atomically (temporary file 0600 in the same directory, `fsync`, rename), directory 0700. Written before any send and after each delivery: an alert is sent once per notifier; only a crash between a delivery and the next write can repeat that one alert. An unwritable state stops the run before anything is sent. Undelivered alerts are retried every cycle for 24 hours, then dropped with an error; an alert queued for a notifier that is no longer configured is dropped for it (logged). One watcher per state file (documented; the example uses a `concurrency` group).
- **Notifiers** (`packages/cli/src/watch/`): the transport is `fetch` POST JSON, no redirects, no referrer, 15 s timeout; errors never carry the URL (it holds the token). Retry: 4 attempts, 1 s / 2 s / 4 s with jitter, honouring `retry_after` up to 60 s (longer → next cycle); only 429, 5xx and network errors are retried. Discord: plain `content`, Vigil's own headline outside a ```` ```text ```` block and everything else inside it (backticks replaced), `allowed_mentions: { parse: [] }`, `SUPPRESS_EMBEDS`, `?wait=true` so success is confirmed; the webhook URL must be `https://{discord.com,discordapp.com,canary.discord.com,ptb.discord.com}/api[/vN]/webhooks/<id>/<token>`. Telegram: plain text, no `parse_mode`, `link_preview_options.is_disabled`, success only when the body says `ok: true`. Messages over the limit drop body lines from the end and say so; the link is always kept.
- **Test-only transport switch**: with `NODE_ENV=test` and `VIGIL_TEST_NOTIFY_ORIGIN=http://127.0.0.1:<port>`, requests go to that local fake server (original host and path kept in the path); any non-local origin is refused, and the variable is ignored outside test mode. The notifier tests exercise the real transport against a `node:http` server; no real Discord/Telegram call is made.
- **Long-running loop**: waits `--interval` between cycles; after consecutive RPC failures, `interval × 2^n` up to max(interval, 15 minutes); SIGINT/SIGTERM stop it between cycles (`CliEnvironment.shutdown`, `sleep`). `--interval` 15–86 400; not allowed with `--once`.
- **`CliEnvironment` additions**: `files` (state), `homeDir`, `notifierHttp()`, `sleep()`, `shutdown`.
- **Replaced test (Phase 6 stub)**: `commands.test.ts` "vigil watch says it arrives in a later version (exit 3)" asserted the Phase 6 stub (decision D5: "a stub until Phase 8"), which this phase replaces by design; it is replaced by tests of the real command's help and usage errors. No other existing test was changed.
- **No new dependency.** `fetch`, `node:http` (tests), `node:fs/promises`, `node:timers/promises`.
